# 골프 부킹·회원권 온라인화 PRD

> **안내(2026-10-24)**: 이 문서의 골프 부킹 기능은 D-87(앱 화면·코드)과 D-88(DB: 테이블·함수·cron·알림 템플릿)로 제거되었다. 부킹 관련 내용은 역사 기록으로 남긴다. 현재 범위는 `docs/DECISIONS.md`를 따른다.

## 배경과 목표

전화로 받던 골프 부킹과 회원권 상담 접수를 온라인으로 옮기고, 운영자의 처리 흐름을 하나의 어드민에서 관리한다. 회원권 계약 체결 자체는 오프라인으로 유지한다.

**현재 문제**

- 요청 내용(골프장, 날짜, 시간대, 인원)을 통화로 받아 누락·오기가 생긴다.
- 진행 상태를 고객이 알 수 없어 확인 전화가 반복된다.
- 고객별 부킹·거래 이력이 개인 메모와 엑셀에 흩어져 있다.

**목표**

- 부킹 요청과 회원권 상담 접수의 온라인 전환율 70% 이상(출시 3개월 시점)
- 요청 접수부터 1차 응답까지 평균 30분 이내(영업시간 기준)
- 모든 상태 변경을 감사 로그로 추적 가능

**비목표 (MVP 범위 밖)**

- 골프장 시스템과의 실시간 티타임 연동, 즉시 확정 예약
- 회원권 대금의 온라인 결제와 에스크로
- 전자계약과 전자서명
- 주민등록번호, 인감 등 고위험 개인정보의 온라인 수집

## 사용자와 핵심 시나리오

| 역할 | 설명 | 주요 행동 |
| --- | --- | --- |
| 고객 (customer) | 골프 부킹 또는 회원권 매수·매도 희망자 | 요청 접수, 대안 수락, 진행 상태 확인, 서류 업로드 |
| 운영자 (admin) | 골프장·고객과 통화하며 건을 처리하는 내부 직원 | 요청 처리, 매물·시세 등록, 거래 단계 관리, 메모 |
| 최고관리자 (owner) | 대표 또는 책임자 | 운영자 권한 관리, 감사 로그 열람 |

**시나리오 A: 부킹 요청**

1. 고객이 카카오로 로그인하고 골프장, 날짜, 희망 시간대, 인원, 예산을 입력해 요청한다.
2. 운영자가 인박스에서 요청을 배정받고 골프장에 전화로 확인한다.
3. 운영자가 티타임과 그린피를 제안하고, 고객은 알림톡 링크로 수락한다.
4. 수락하면 확정되고 확정 알림톡이 발송된다. 제안에는 유효시간이 있어 지나면 만료된다.

**시나리오 B: 회원권 매수**

1. 고객이 매물 리스트와 시세를 보고 상담을 신청한다.
2. 운영자가 통화하며 가격을 협의하고, 거래 단계와 메모를 갱신한다.
3. 계약 일정을 확정하고 필요 서류 체크리스트를 고객에게 보낸다.
4. 오프라인 계약, 잔금, 명의개서가 끝나면 완료 처리하고 매물을 판매완료로 바꾼다.

## 비기능 요구사항

상태 변경은 서버의 단일 경로로만 일어나고, 감사 로그와 같은 트랜잭션에 기록된다.

**정합성**

- 상태 전이는 Postgres 함수(`rpc`)에서만 수행하고, 허용된 전이만 통과시킨다. 클라이언트의 `status` 직접 update는 RLS로 막는다.
- 매물 선점은 조건부 update(`WHERE status = 'listed'`)로 처리하고, 영향 행이 0이면 충돌로 응답한다.
- 한 부킹 요청에 수락된 제안은 1건만 허용한다: `UNIQUE (request_id) WHERE status = 'accepted'`.
- 요청 생성과 수락 API는 `Idempotency-Key`를 받아 중복 제출을 막는다.
- 금액은 `bigint` 원 단위로 저장하고, 시간은 `timestamptz`로 저장해 KST로 표시한다.

**보안과 권한**

- 모든 테이블은 RLS를 켜고 기본 거부로 둔다. 고객은 `user_id = auth.uid()` 행만 읽는다.
- 운영자 여부는 `app_metadata.role` custom claim으로 판별한다. 사용자가 수정할 수 있는 `user_metadata`는 쓰지 않는다.
- `service_role` 키는 서버 전용 환경변수에만 두고 `NEXT_PUBLIC_` 접두사를 금지한다.
- 어드민 경로는 middleware와 서버 양쪽에서 역할을 검사한다. 운영자 계정에는 MFA를 강제한다.
- 부킹 요청·상담 신청에 사용자별 rate limit을 둔다(예: 10분당 5건).

**감사 로그**

- `audit_logs`는 append-only다. update와 delete 권한을 모든 역할에서 회수한다.
- 기록 항목: actor, 대상 엔티티와 id, action, before/after JSON, IP, user-agent, 시각.
- 서류 다운로드(서명 URL 발급)도 열람 이력으로 남긴다.

**개인정보**

- 주민등록번호, 인감, 신분증 사본은 온라인으로 수집하지 않는다. 업로드 양식에도 안내 문구를 넣는다.
- 서류는 private bucket에 두고, 5분 TTL의 signed URL로만 제공한다.
- 휴대폰 번호는 목록 화면에서 마스킹한다. 탈퇴 및 보관기간 경과 시 파기 배치를 둔다.

**가용성과 알림 신뢰성**

- 알림은 transactional outbox로 발송한다. 상태 변경 트랜잭션에서 `notification_outbox`에 적재하고, pg\_cron과 Edge Function이 1분 주기로 발송한다.
- 재시도는 지수 백오프로 최대 5회 하고, 그래도 실패하면 DLQ 상태로 두고 운영자에게 알린다.
- 만료된 제안과 SLA 초과 건은 pg\_cron으로 주기적으로 처리한다.
- 에러는 Sentry로 수집하고, Supabase 일일 백업을 확인한다(PITR은 요금제에 따라 검토).

## 기술 스택과 아키텍처

프론트와 BFF는 Vercel의 Next.js가, 데이터·인증·스토리지·배치는 Supabase가 맡는다.

| 영역 | 선택 | 비고 |
| --- | --- | --- |
| 프론트 | Next.js App Router, TypeScript, Tailwind, shadcn/ui | Server Component 우선, 모바일 우선 UI |
| 서버 로직 | Server Actions, Route Handlers | 입력 검증은 zod, 상태 전이는 DB 함수 호출 |
| DB | Supabase Postgres | RLS, `rpc` 함수, migration은 Supabase CLI로 관리 |
| 인증 | Supabase Auth(카카오 OAuth, Phone OTP) | `@supabase/ssr`로 쿠키 세션 |
| 파일 | Supabase Storage(private bucket) | signed URL 5분 |
| 배치 | pg\_cron, Supabase Edge Functions | outbox 발송, 제안 만료, SLA 감시 |
| 알림 | 카카오 알림톡 대행사(Solapi 등) | 템플릿 사전 심사 필요 |
| 타입 | `supabase gen types` | DB 스키마에서 TS 타입 자동 생성 |
| 테스트 | Vitest, Playwright, pgTAP | RLS와 상태 전이는 pgTAP으로 검증 |
| 관측 | Sentry, Vercel Analytics |  |
| 환경 | local, preview(Vercel PR), production | Supabase 프로젝트도 dev/prod 분리 |

디렉터리는 역할별 route group으로 나눈다: `app/(customer)`, `app/(admin)/admin`, `app/api`. 도메인 로직은 `lib/domain/{booking,membership}`에 두고 UI에서 분리한다.

## 단계별 릴리스, 성공 지표, 오픈 이슈

| 단계 | 범위 | 출시 기준 |
| --- | --- | --- |
| MVP | F-01\~06, A-01\~06, N-01\~02 | 운영자 2명이 1주간 전화 없이 신규 요청 100%를 어드민으로 처리 |
| 2단계 | F-07\~08, A-07, N-03, 부킹 예약금 결제(토스페이먼츠) | MVP 전환율 50% 도달 |
| 3단계 | 확보한 티타임 블록의 즉시 확정, 전자계약 연동 검토 | 주요 골프장과 블록 계약 확보 |

**성공 지표**

- 온라인 접수 비율(전체 요청 중 웹 접수)
- 요청부터 1차 응답까지 시간, 요청부터 확정까지 시간
- 부킹 확정률(확정 / 요청), 회원권 상담의 계약 전환율
- 알림 발송 성공률(목표 99% 이상)
